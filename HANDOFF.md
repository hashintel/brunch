### Builder Charter

Implement the review cleanup in an intentionally breaking order.

The user explicitly wants semantic cleanup first, even if the review UI breaks in the meantime.

#### Product model to implement

1. Requirements and criteria review are **not** item-by-item approval workflows.
2. Earlier phases may still surface requirement-like or criterion-like material, but that material is **synthesis input**, not canonical accepted output.
3. The review phase is the authority boundary where the system presents a **candidate set**.
4. That candidate set should be **turn-owned**.
5. `accept review` promotes the current turn-owned candidate set into the canonical surviving requirements / criteria.
6. `request changes` keeps the phase open and causes a revised successor review turn; it does **not** create canonical carry-forward state.
7. Downstream phases and export read the **accepted surviving set directly**, not a larger entity pool filtered by `reviewStatus`.
8. `reviewStatus` should stop being a first-class concept for requirement / criterion entities.
9. Sidebar badges for approved / rejected / pending requirements / criteria should disappear as part of the cleanup.
10. Temporary UI breakage during this cleanup is acceptable and expected; it is treated as an ad-hoc red test.

#### Refactor / build sequence

##### Phase 1 — Aggressive semantic deletion (expected red phase)

Delete the legacy semantics first.

- Remove `reviewStatus` from requirement / criterion entities and shared API types.
- Remove targeted `requirementReview` / `criterionReview` payloads and the item-by-item review path.
- Remove server logic that records one-item approval / rejection links as the primary review semantics.
- Remove manifest walkthrough history that still encodes item-by-item review questions.
- Remove UI affordances that display requirement / criterion review badges.

Expected outcome: tests and/or review UI should fail because the old assumptions are no longer being silently supported.

##### Phase 2 — Introduce accepted-set authority

Replace the deleted semantics with one accepted-set seam.

- Review turns must carry a synthesized candidate set as part of the turn-owned assistant artifact.
- Acceptance promotes that candidate set into the canonical surviving requirement / criterion collection.
- Request-changes leaves the candidate set non-canonical and generates a revised successor review turn.
- Closeability, criteria-generation context, and export must read the accepted set instead of `reviewStatus`.

Recommended constraint: prefer the smallest implementation that makes the accepted set durable enough for replay/resume. Do **not** preserve `reviewStatus` as a compatibility crutch.

##### Phase 3 — Rebuild review UI on the cleaned contract

- Rebuild requirements / criteria as review-specific surfaces, not generic question cards.
- Render the turn-owned candidate set, stable codes, the two review actions, and one note field.
- No per-item approval affordances.
- No sidebar status badges.

##### Phase 4 — Repair follow-on demo seams

- Requirements accept → criteria kickoff
- Criteria accept → export-ready completion
- Transcript replay / hydration should preserve the review framing and accepted review summaries coherently
