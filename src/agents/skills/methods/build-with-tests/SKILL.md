# build-with-tests

Use this method after an execute-mode task brief is clear enough to build. If the brief does not mention the current execute foothold, call `execute_status` first when available and confirm that the requested action is actually ported. If the brief needs spec truth, call `execute_snapshot` or rely on a task brief that already names the snapshot facts it used; if it claims plan readiness, call `execute_plan_check` or cite the plan-check result already present in the brief; if it claims a plan shape, call `execute_plan_outline` or cite the outline already present in the brief; if it claims executable-plan-shaped data, call `execute_plan_draft` or cite the draft already present in the brief; if it claims old-cook compatibility, call `execute_cook_plan_preview` or cite the preview already present in the brief; if it explicitly needs a bounded executable cook plan file, call `execute_cook_plan_file` and report the written `.brunch/cook/specs/<specId>/plan.yaml` path; if it asks whether cook can launch, call `execute_cook_launch` and report `missing_plan` or `ready` plus `runStatus: not_started`; if it asks to create a cook run, call `execute_cook_run_create` and report the metadata path plus the fact that worktrees/slice execution remain pending; if it asks to create the run worktree, call `execute_cook_worktree_create` and report the empty worktree path plus the fact that host source population and slice execution remain pending; if it asks to populate the worktree, call `execute_cook_populate` and report the copied plan path plus the fact that host source copy remains pending; if it asks to choose source policy, call `execute_cook_source_policy` and report that host source files were not copied; if it asks to copy host source, call `execute_cook_source_copy` and report copied entries plus the fact that slice execution remains pending; if it asks to initialize reports, call `execute_cook_report_init` and report the `reports.jsonl` path plus the fact that no slice events have run; if it asks to mark a slice started, call `execute_cook_slice_start` and report that no agent/test execution happened; if it asks to request slice execution, call `execute_cook_slice_execute` and report that only an agent request artifact was written; if it asks to ingest an agent result, call `execute_cook_agent_result` and report that no tests have run; if it asks to ingest a test result, call `execute_cook_test_result` and report that tests were not run by Brunch; if it asks to complete the active slice, call `execute_cook_slice_complete` and report that no Petri or promotion happened. Do not call `execute_plan_outline_artifact`, `execute_plan_draft_artifact`, `execute_cook_plan_file`, `execute_cook_run_create`, `execute_cook_worktree_create`, `execute_cook_populate`, `execute_cook_source_policy`, `execute_cook_source_copy`, `execute_cook_report_init`, `execute_cook_slice_start`, `execute_cook_slice_execute`, `execute_cook_agent_result`, `execute_cook_test_result`, or `execute_cook_slice_complete` unless persistence of that artifact/file/run metadata/worktree/population/policy/source-copy/report log/slice marker/request/result/test-result/completion itself is part of the user request. `execute_cook_launch` is validation only; `execute_cook_run_create` creates run metadata only; `execute_cook_worktree_create` creates an empty directory only; `execute_cook_populate` copies the plan into the worktree only; `execute_cook_source_policy` records policy only; `execute_cook_source_copy` copies bounded host source entries only; `execute_cook_report_init` writes an initial run-ready report only; `execute_cook_slice_start` appends a slice marker only; `execute_cook_slice_execute` writes a request only; `execute_cook_agent_result` ingests a prewritten result only; `execute_cook_test_result` ingests a prewritten test result only; `execute_cook_slice_complete` marks completion only; none compiles Petri. Work like a disciplined coding agent inside Brunch's deterministic execution harness: understand the surrounding code, write or strengthen the relevant tests, implement the smallest coherent behavior, and report the evidence. Passing tests are necessary, but they are not a license to ignore the task brief, design context, accessibility, integration, or user-visible quality constraints that were pushed into the prompt.

Start by reading existing tests and nearby implementation. Match the repository's naming, imports, public interfaces, and error-handling conventions. Prefer public-interface tests that fail for the missing behavior, not private implementation assertions or trivially passing checks. If the task is UI-facing, include the behavior users observe: states, accessibility affordances, responsive behavior, or visual integration with the existing design system when those are part of the brief.

Then implement in small steps. Keep the implementation local to the scoped task unless the brief names a shared seam. Do not weaken tests to make progress. Do not use direct shell or file-write authority unless the active tool policy exposes it; execute mode may route code changes through code-owned tools rather than raw Pi builtins.

Report the outcome as evidence, not self-praise:

- tests/probes run and their result
- files or surfaces changed
- deviations from the task brief
- remaining risks or blocked follow-ups

If the build reveals that the plan topology is wrong, do not freelance a new topology. Emit the finding for adaptive replan: what should split, merge, reorder, or be clarified, and what evidence led to that conclusion.
